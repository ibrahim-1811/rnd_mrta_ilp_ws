Big picture

Three files go in. A fixed simulator runs them. Only one part changes between experiments: the strategy that decides which robot gets which order. Map, roads, traffic, battery, speed and service times are identical for every strategy, so a difference in the results is caused by the strategy.

The research chain is State → Decision → Outcome. The decision is recorded before anything moves; the outcome is recorded after the order is delivered. The two are joined only by a decision id, so the learner can never see the future.

The decision loop

Whenever one or more robots become free, one decision happens. A run of 300 orders on W100 makes a few hundred.

  1. Find the free robotsIdle, and not due to charge. At or below 10% a robot finishes its current order and then goes to charge instead.
  2. Hold briefly, if batching is onWith a dispatch quantum (--quantum 3.0) freed robots wait a moment so several are assigned together. Off by default.
  3. Choose the orders on offerThe oldest waiting orders, as many as the fleet has robots. If none of them can be served, the window reaches further down the queue so the run cannot stall.
  4. Score every robot × order pairDirected A* distance through the one-way roads, through every shelf of the order in the best visiting order, to the drop-off. Plus the energy needed: the order, the trip to the nearest charger, and the 10% reserve.
  5. Remove pairs a robot cannot affordThe battery check is a hard rule for every strategy, and the executor re-checks every pair a strategy returns.
  6. Record the decisionEvery pair and its scores are written before anything is chosen or moves. A test proves the recorded rows cannot contain the future.
  7. The strategy choosesThe only step that differs between strategies. All three run the same greedy sweep over a different ranking.
  8. Build the missions and hand them to the engineEvery robot's route is the directed A* route, whatever the strategy ranked on.
StrategyRanks pairs byRole
nearest_astarreal driving distance (directed A*)the grid-aware baseline
nearest_manhattanstraight-line grid distance, ignoring walls and one-way roadsthe naive control: shows what grid-awareness is worth
randoma seeded shufflethe floor every strategy must beat

The engine

Between decisions the engine moves the fleet on one simulated clock, kept as exact fractions so a run is identical every time. It never decides who gets which order.

State machines

An order

stateDiagram-v2
    [*] --> PENDING: loaded from the CSV
    PENDING --> ASSIGNED: a strategy picks it
    ASSIGNED --> IN_PROGRESS: robot sets off
    IN_PROGRESS --> COMPLETED: dropped off
    COMPLETED --> [*]

FAILED also exists in the schema and is never expected in a clean run.

A charger or holding slot

stateDiagram-v2
    [*] --> FREE
    FREE --> RESERVED: claimed before the robot moves
    RESERVED --> OCCUPIED: robot arrives
    OCCUPIED --> VACATING: robot starts to leave
    VACATING --> FREE: robot is back in the aisle

A slot is offered only while FREE, so no robot can drive into a cell another robot owns, stands on, or is backing out of.

Rules every map must meet

  • Roads are one-way: two neighbouring cells never point at each other.
  • Every road cell has an arrow out.
  • No arrow points into a station or a wall. Robots enter any station from a neighbouring road by themselves, and never drive through one.
  • Every station touches a road, and from any road every other road can be reached.
  • For a large fleet: no rotaries, 2 × 2 loops where four robots can lock each other forever.

Values are stored raw, never as ready-made predicates such as battery_high: where a threshold goes is the learner's experiment. Exact numbers (clock, charge) are stored twice, as a float and as an exact fraction string. Identifiers like robot_003 are labels only, never facts to learn from. On V2, 100 orders give 1,973 decision rows (100 positive, 1,873 negative examples) and 100 outcome rows.

ROS and Gazebo

Optional, for watching. One world, built from the current map, holding the warehouse only. Starting Gazebo (gazebo.launch.py) first stops any Gazebo already running this world, then loads a temporary copy of the world with the run's robots parked on their start cells, so they appear with the warehouse. When a run starts the fleet node finds them; if the run asks for a different number it creates the missing ones or removes the extra. The node runs the same decision loop and engine as the headless runner, so a live run and a headless run produce byte-identical datasets.

Rules that must not break

From CLAUDE.md and ARCHITECTURE.md. A change that breaks one of these is a regression, whatever else it improves.

  • Only the allocation strategy varies. No strategy may change routing, traffic, battery drain, charger policy, speed or service time.
  • One simulated clock in exact fractions; no wall-clock time in any result.
  • Ordinary roads are one-way; zero uncontrolled two-way road edges.
  • Stations are never used as shortcuts, and robots never hop from one station to another.
  • Traffic never changes which robot owns which order.
  • The battery check is a hard rule, applied identically to every strategy.
  • Decision data contains nothing that happened after the decision.
  • The charge bookkeeping is exact; a charger slot is offered only while free.
  • robot_id may break an exact tie, and is never a learned feature.
  • Gazebo contains no planning. It shows what the simulator decided.
  • Orders have exactly order_id, item_id, shelf_id, quantity, dropoff_id; no priority, release time or deadline.

Known issues and open decisions

traffic

A circle of waiting robots cannot be untangled

If robots form a closed loop each waiting for the next, the run stops with STALLED and a CYCLES report. The circle that happens in practice is the 2 × 2 rotary; W100 has none and the checker warns on every one. V2 has 33, and one caused the deadlock under the random strategy. .scratch/traffic-liveness/issues/01

commit

Most recent work is not committed

Decision window, recording, strategies, drawn maps, W100, the docs reorganisation. Review git status before committing.

battery

Fixed: Stage Zone robots now return to work

At 100 robots, robots that asked for a charger while every charger and holding cell was full used to wait on a Stage Zone for the rest of the run (36 of 100). Approved 2026-10-24 (DECISIONS.md, "Stage Zone Promotion"): they now queue with the holding robots, lowest SOC first, and take a freed charger they can reach. 100 robots / 2000 orders: 100 charge sessions instead of 64, none left on a Stage Zone, makespan 2441.29 s → 2133.49 s, 0 violations. Preemption itself (CHARGE_DUE only) still never fires by order volume and is covered by its own tests.

Its premise is stale: one-way roads removed the head-on conflicts it looks for. The behaviour is covered by three passing checks. .scratch/traffic-demos/issues/01
