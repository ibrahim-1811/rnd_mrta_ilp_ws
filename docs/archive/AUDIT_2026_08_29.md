# Executive summary

This repository is a **well-engineered MRTA simulation testbed whose research
contribution has not been started**.

The engineering is genuinely good. Five ROS 2 packages build from scratch with zero
errors and zero warnings in under 12 seconds. Forty-three unit tests pass. The complete
pipeline — orders → allocation → A\* planning → robot execution → pickup → delivery →
CSV output — was executed 25 times during this audit without a single failure, with up
to 8 robots running concurrently. The design's best property is real: the simulator
drains battery using the *same* `path_energy_percent` function on the *same* path that
the allocator used to score the candidate, so predicted and realised costs agree by
construction rather than by calibration.

The research contribution is absent. **There is no ILP implementation** — no learner, no
solver library, no Prolog runtime, no learned rule file, and no allocator by that name.
**Nothing is outcome-aware**: the only realised-outcome message in the system
(`/fleet_travel_stats`) is consumed purely to decrement a counter, and both of its
payload values are discarded. The trace CSV that would be training data has no outcome
column at all.

Beneath that sits a subtler and more urgent problem. Three hard-coded values —
`priority = 1`, `deadline = now + 300`, and a structural invariant that makes
`workload ≡ 0` for every candidate — silently disable four of the six terms in the
proposal's cost equation. The measurable consequence is that **thirteen strategy names
collapse into five distinct behaviours**, and the total outcome spread across *all*
strategies is 0.7 % in distance and 1.9 % in energy. The baseline comparison the
research depends on does not currently discriminate between the policies it compares.
The test suite passes without detecting this, because the strategy tests use synthetic
candidates in a state the real pipeline cannot produce.

The ICAPS 2026 presentation in `docs/` reports ILP results, makespan tables, and an
explanation study. Those came from a **different, earlier workspace**, archived
git-ignored at the repository root as `ilp_ws.zip`. **They are not reproducible from
this repository.**

The substrate is ready to host the research. The research has not begun.

# Algorithms

**12 registered strategies + 1 alias = 13 usable names.** All implemented, unit-tested,
and verified running end to end:

`random`, `round_robin`, `nearest`, `least_busy`, `highest_battery`, `spt`, `lpt`,
`edf`, `heuristic` (alias `greedy`), `score`, `bid`, `auction`.

Composite cost (`features.py:59`), implemented exactly as written:

```
C_ij = λ1·T_ij + λ2·D_ij + λ3·G_ij + λ4·E_ij + λ5·W_i − λ6·q_j
λ1=0.05  λ2=0.03  λ3=1.0  λ4=0.10  λ5=1.0  λ6=1.0     (all hard-coded)
```

**Not implemented:** Hungarian, Genetic Algorithm, Manual Prolog, Single-Teacher ILP,
Multi-Teacher ILP, Outcome-Aware ILP. No optimisation or ILP solver library (`pulp`,
`mip`, `cvxpy`, `ortools`, `scipy.optimize`, `linear_sum_assignment`) appears anywhere in
the tree or in any `package.xml`.

## The central algorithmic finding

Three hard-coded values silently disable four cost terms:

| Value | Location | Effect |
|---|---|---|
| `priority = 1` | `task_manager.py:155` | λ6·q is a constant offset — cannot change any argmin |
| `deadline = now + 300.0` | `task_manager.py:156` | all deadlines equal → `edf` ≡ FIFO |
| `workload ≡ 0` | structural | λ5·W contributes nothing |

`workload ≡ 0` is structural, not incidental: a robot is a candidate only while
`is_available`, and `_assign` marks it busy the instant workload becomes 1. **Measured:
`workload = 0` in 1,396 of 1,396 logged candidate rows** across 25 runs; `priority = 1`
in every row.

Provable consequence — with `W ≡ 0` and `q ≡ 1`, `C_auction = C_bid − 1`, and both
maximise `1/(1+C)`, which is monotone in `C`. **The argmax is the same robot.**

### Measured behavioural collapse (4 robots, 10 orders, seed 42)

All 13 names run end to end, clustered by task→robot assignment signature:

| Class | Names behaving **identically** |
|---|---|
| 1 | `nearest` · `least_busy` · `spt` · `edf` · `heuristic` · `greedy` |
| 2 | `score` · `bid` · `auction` |
| 3 | `highest_battery` · `lpt` |
| 4 | `round_robin` |
| 5 | `random` |

**13 names → 5 distinct behaviours.**

Under contention (8 robots, 40 orders) several separate, but `nearest ≡ least_busy ≡
spt` persists and the outcome spread stays negligible:

| Strategy | mean travel (m) | mean energy (%) | deferrals |
|---|---:|---:|---:|
| nearest / least_busy / spt / lpt | 45.375 | 13.719 | 0 |
| highest_battery | 45.375 | 13.873 | 0 |
| heuristic | 45.375 | 13.844 | 1 |
| score | 45.475 | 13.772 | 0 |
| auction | 45.475 | 13.786 | 1 |
| random | 45.525 | 13.835 | 0 |
| round_robin | 45.675 | 13.976 | 0 |

Full spread: **0.7 % distance, 1.9 % energy** — with no repetitions to establish whether
that is signal.

### Latent defect

`_AuctionBase._bid` computes `1.0 / (1.0 + C_ij)` where `C_ij` includes `− λ6·q_j`.
Currently unreachable (`q ≡ 1` keeps the denominator non-negative), but a task with
`q_j ≥ 2` drives it to zero or negative → `ZeroDivisionError`, or negative bids silently
discarded by the `> 0.0` guard. **This fires the moment priorities become variable.**

## "What makes it Outcome-Aware rather than a weighted assignment optimizer?"

**Nothing in the code justifies the phrase.**

The test is whether realised execution results influence future decisions. They do not:
`/fleet_travel_stats` carries `travel_dist` and `battery_consumed`;
`task_manager._on_travel_done` (`task_manager.py:160-173`) reads **neither**, using the
message only to decrement `workload`, increment `_completed`, and publish `/end_order`.
No predicted-vs-actual comparison exists. `cumulative_load` accumulates the *predicted*
`proc_time` and is never corrected. The trace CSV's only label is `is_chosen` — what the
teacher *did*, not how it *turned out*.

What exists is a **greedy per-task weighted-sum selector** over pre-execution
predictions — and, with λ5 and λ6 inert, effectively a weighted sum of time, distance,
congestion and energy.

**Preparatory assets that do exist:** `symbolic.py`'s complete predicate vocabulary
(unused, and with a 0–1 vs 0–100 battery unit mismatch); the correctly-shaped trace
dataset; and the prior workspace in `ilp_ws.zip`.

The presentation reports a Popper-learned policy, makespan tables for 6 strategies × 4

# Grid awareness status

**PARTIAL.**

Implemented and verified: `WorldGrid` metre↔cell mapping (31×31 at defaults), 4-connected
A\* with an admissible Manhattan heuristic, ASCII obstacle map loading, and a shared world
between simulator and allocator.

**Is `c(e,k) = α·distance + β·obstacle + γ·congestion` implemented? No.** What exists is
a two-level cost:

- **Edge level** (`grid.py:93`): `step_cost = 1.0 + congestion_weight · congestion(next)`
  — two terms only. The distance coefficient is a fixed literal `1.0`, not a tunable α.
  **There is no β obstacle term**: obstacles are a hard constraint, removed from
  `neighbors()`, i.e. infinite cost rather than a penalty.
- **Allocation level** (`features.py:59`): the 6-term `C_ij`, used only by `score`,
  `bid` and `auction`.

**Obstacles are unusable end to end:**

- No map files ship — `simulation_env/setup.py` globs a non-existent `maps/`.
- Neither launch file exposes `grid_map_file`.
- `task_manager.py:61` builds its `WorldGrid` **with no obstacles at all**, so the
  allocator would plan through walls the simulator routes around.

**Every measurement in this repository was taken on a completely empty grid.**

Also: `WorldGrid.to_cell` **silently clamps** out-of-range coordinates, making
`headless_shelves_100_large.csv` (X ±45 m, Y to 95 m) quietly unusable at the default
30 m world.

# Congestion status

**PARTIAL — an occupancy heuristic, not a congestion model.**

Implemented: the simulator tracks `occupancy[cell]`, publishes it at 1 Hz on
`/simulation/congestion`, and the task manager feeds it into A\*, which prices congested
cells.

Not implemented: **path reservations** (planned routes contribute nothing), **temporal
reasoning** (no time-indexed occupancy, no space-time A\*), **collision avoidance**
(robots pass through each other freely), **waiting cost**, and **re-planning during
motion** (A\* runs once per leg, then the path is followed blindly).

Congestion is the count of robots standing on a cell *right now* — typically 0 or 1.
Observed values 0–3, dominated by the drop-off spawn cluster rather than route
contention. Data is up to 1 s stale at the allocator (1 Hz publish vs 5 Hz decisions).

With λ3 = 1.0, a congestion value of 1.0 contributes as much to `C_ij` as an entire 33 m
distance term — so it is not negligible in the cost function; it is simply not measuring
route conflict. For a thesis claiming grid-aware congestion-sensitive allocation, this
is the weakest link.

# Reproducibility

**PARTIAL — and this is a P0 problem.**

Positive: no hard-coded user or absolute paths anywhere in `src/` or `scripts/` (searched
for `/home/`, `/Users/`, `C:\`, `~/` — clean). Loggers call `expanduser`/`expandvars`.
`run_experiment.sh` derives its own repo root. Dependencies are limited to
`ros-jazzy-desktop`; `mrta_core` is stdlib-only.

**Reproducible:** the order stream, and the **assignment sequence** — repeated runs of
`nearest` and `score` at seed 42 produced byte-identical task→robot mappings and
identical `mean_travel_m` / `mean_energy_pct`.

**Not reproducible: the logged features themselves.** Diffing two identical-seed
`nearest` runs (ignoring timestamps) showed assignments identical but features differing:

```
run A:  order_3_task_3 ... travel_time=13.766  congestion=1.0  energy_pct=6.256
run B:  order_3_task_3 ... travel_time=9.426   congestion=3.0  energy_pct=5.522
```

**Root cause:** the simulator advances via `time.sleep` against wall clock with one
thread per task, and congestion is sampled at the instant of each decision. `makespan_s`
is likewise wall-clock (3.751 vs 3.756 s for identical inputs) and depends on machine
load.

Consequences: makespan and throughput are not valid scientific quantities as computed;
the ILP training data cannot be regenerated identically from a seed; and cost-based
strategies could in principle flip a close decision between runs (not observed, but
nothing prevents it).

Other reproducibility notes: no `requirements.txt`, `pyproject.toml` or `rosdep.yaml`
(none currently needed); `configs/` and `data/*` are empty and unused; and **`README.md`
is untracked**, so a fresh clone lacks the project's primary documentation.

# Overall assessment

```
Engineering implementation:     70%
Research/scientific completion: 15%
Documentation/reproducibility:  55%
```

**Engineering — 70 %.** Five packages build with zero warnings; 43 unit tests pass; the
full pipeline runs reliably end to end with concurrent robots; A\*, the physics model,
the battery lifecycle, and 12 strategies are all genuinely implemented and verified. The
shared world/physics model between simulator and allocator is a real design achievement.
Deductions: no node or integration tests (~60 % of production code untested); obstacles
not wired end to end; congestion modelled only as instantaneous occupancy; key parameters
unreachable from launch files; several pieces of dead code; and a latent division defect.

**Research — 15 %.** The credit is for genuine groundwork: a correct grid-aware feature
pipeline, a physics-consistent cost model, 12 baseline strategies, a well-shaped trace
dataset, and a complete (if unwired) symbolic vocabulary. But the contribution named in
the title does not exist — no ILP, nothing outcome-aware, no explanation generation —
and the layer beneath it is compromised: four of six cost terms are inert, 13 strategies
collapse to 5, the outcome spread is under 2 % with no repetitions, timing is wall-clock,
and there is no experiment automation or statistics. **No result in this repository is
currently publishable**, and the ICAPS material describes a different system.

**Documentation/reproducibility — 55 %.** The root README was already accurate and
useful, and this audit adds 19 cross-referenced technical documents traceable to source.
The build is clean and dependency-light with no machine-specific paths, and the pipeline
reproduces its assignment sequences exactly. Deductions: the README is **untracked** (a
fresh clone lacks it); logged features and wall-clock timings are **not** reproducible;
there is no run manifest, so results are not self-describing; and empty `configs/` and
`data/` directories suggest an intended structure nothing uses.

These figures are deliberately not rounded upward. The 70/15 gap is the accurate picture:
**a well-built testbed with the experiment and the contribution still ahead of it** — which
is a considerably better position to be in than the reverse.
