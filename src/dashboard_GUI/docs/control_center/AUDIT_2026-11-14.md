## 4. UI quality findings (ranked by impact)
1. **No results/analytics surface (screens above).** The product's purpose (campaign comparison) has no screen; Run history lists directory names and hashes (`run_history_1440.png`), not strategy/metric columns.
2. **Two default data paths are unusable on this repo:** `/runs` default scope times out (>60 s) and `/experiments` returns 413 on 10,346 directories (section 2). The Experiments "Repository" tab and Run history "Repository history" tab depend on these (`HistoryView.tsx:9,25`, `App.tsx`/`ExperimentsView`); not clicked, so the on-screen error is unverified.
3. **Misleading capability labels:** System shows "Learned rules: Unavailable" while ILP runs exist; the Operations toolbar label reads "ROS / Gazebo session" for the auto-selected newest job (a cancelled Gazebo job), and Run status "Cancelled" is the first thing seen on load (`operations_1440.png`) because the newest job is auto-selected (`App.tsx:60`).
4. **Tiny type:** most UI text is 10-11 px (root 13 px; `styles.css` uses `font-size:10px` on labels, buttons, tables, badges; 7-8 px on brand subtitle, `.sample-count`, `.mini-tag`, `.map-legend` at <1250 px). Measured: 20 buttons/selects/inputs at 10 px in the DOM at 1440 px. Readability and accessibility problem for a projector/demo.
5. **Low contrast:** muted green-grey text `#8b9680`, `#a0aa90`, `#b4c4a0`-style values on `#fff/#f5f6f1` (e.g. field hints, table values `#89a36c`, "Unknown" cells in `run_history_1440.png`). Estimated well below WCAG AA 4.5:1 for several (visual estimate and hex values only; no contrast tool run).
6. **No dark theme:** no `prefers-color-scheme` rule in `styles.css`; `getComputedStyle(body).backgroundColor` is transparent over a fixed light `#f5f6f1` root; sidebar is dark green only. If dark mode is wanted, the colours are hard-coded hex in one 9-line minified stylesheet (`frontend/src/styles.css`, 9 lines), so theming means a variable refactor.
7. **Focus styles are browser defaults:** only `outline-offset:4px` is set (`styles.css` line 1); no custom `:focus-visible`. A skip link exists (`App.tsx:105`) and nav uses `aria-current` and `aria-label` (good).
8. **Responsive behaviour is decent:** at 400 px no horizontal overflow (`scrollWidth` 400 on all 5 screens), sidebar collapses to icons, panels stack (`operations_400.png`). Defects: map overlay text collides ("No fleet observation selected" overprinting "Drag to pan"), the sidebar icons lose labels with no tooltips, page height 3291 px on Operations. Full-page screenshots show the fixed sidebar ending at viewport height; this is a capture artefact (`position:fixed`, `styles.css`), not a user-visible bug.
9. **Layout/typography consistency is good** (consistent cards, eyebrow + title pattern, consistent green palette, Inter/system font), but the Operations screen puts run setup, map, fleet, logs and metrics in one 1700 px page, and the System page leaves large empty card space (`system_1440.png`: the first card is mostly blank; provenance card shows truncated hashes `fbab9056ece33112…`).
10. **Empty and error states are present and honest** (Fleet "No fleet observation", metrics "—", error banners with `role=alert`, `App.tsx:106`, `App.tsx:120`), which is a strength. Experiments library shows only an empty select (`experiments_1440.png`).
11. **No charts at all** and the 2D map is a static lane view; legend labels (Shelf, Staging, Drop-off, Charging, Holding) are good.

## 5. Technical risks
- **W100 hard-coding (all places found by grep):** backend `adapters/catalogue.py:30-31,52,68`; `api/routes.py:70,122`; `adapters/commands.py:174`; `adapters/gazebo.py:151`; `schemas/jobs.py:29,116`; frontend `App.tsx:51,111,151,153`, `GazeboSetup.tsx:20,32`, `model.ts:19`, `InputPicker.tsx:12`. The config path is also fixed (`catalogue.py:9`, `src/simulation_env/config/warehouse.yaml`), and `config.map_path` must be W100. Every job validator resolves the scenario through `load_scenario()` (e.g. `adapters/inputs.py:59`, `adapters/validation.py`). Hashing the map inside `build_manifest` is by config, so a second map needs the config object replaced, not just a different scenario id.
- **Runner-hash guard:** `observed_runner.py:18` (`11b49c...`) vs. current `run_workload.py` (`2852ee...` per `docs/control_center/MERGE_2026-11-14.md`). It is a deliberate parity check; simply updating the constant would bypass the review it exists for. The merge note says the adapter must be reviewed against the new `--map` runner first. Consequence: live view, telemetry playback and 4 backend tests + 19 errors (MERGE note, not re-run by me).
- **Upload of an xlsx must flow through the existing validators,** not a new one (CLAUDE.md: maps must pass topology, routing, traffic, terminal-reachability): (1) store content-addressed copy like `InputStore.add` (`adapters/inputs.py`), size-limited; (2) run `map_tool.py check` (`src/simulation_env/scripts/map_tool.py:116`, `cmd_check`: loads with `load_warehouse_xlsx`, reports errors by Excel cell, prints "FAIL"/status) as a subprocess and surface its text; (3) run `check_map_topology.py` (`src/simulation_env/scripts/check_map_topology.py`, about 3 minutes per `src/simulation_env/test/test_heldout_map.py:6`) as a queued job, not inside a request; (4) only then register the map as selectable; (5) the runner accepts a map by name from `maps/` via `--map` (`sim_config.py:136-147`, `run_workload.py:68,243-248`), but requires an orders file generated from that same map, so order generation per map is a separate piece of work and a CSV validated against W100 (`inputs.py:59`) would be wrongly checked. Writing uploads into `src/simulation_env/maps/` would mutate a research directory; they should go under `var/` and be passed by absolute path (supported by `resolve_map_name`, "an absolute path" at `sim_config.py:140`).
- **Discovery cost:** `RunIndex.rebuild()` walks everything under `runs/` (10,346 dirs); needs a fixed registry of roots (`runs/campaign/final`, `.../transfer`) or an explicit campaign reader.
- **Execution lock:** "Only one dashboard-owned process may run at a time" (`App.tsx:157`); a replay or campaign viewer must be read-only and not use the job gate, otherwise it would conflict with the owner's Gazebo runs.
- **Scientific-boundary risk for replay:** a 2D replay must read recorded artifacts, never plan routes in the dashboard (CLAUDE.md Gazebo rule applies equally).

## 6. Suggested increment order (small, each independently reviewable)
1. **Fix discovery and labels (low risk, no science):** make `/runs` and `/experiments` not scan all of `runs/` (explicit roots), correct the `ilp`/`replay` capability flags, stop auto-selecting a cancelled Gazebo job.
2. **Campaign results screen, read-only:** list `runs/campaign/{final,transfer}` -> `stats/*.csv`, per-fleet `summary.csv`/`paired.csv`, `explain/*`; add tables, the first bar/line charts (add one chart library or hand-rolled SVG), link to `m8_final_campaign.html`.
3. **Strategy and rule picker:** endpoint listing the 12 rule artifacts; Operations/Experiments dropdown by arm name; allow `ilp` in the experiment matrix only if the experiment runner supports it (not verified here).
4. **Map selection from `maps/*.xlsx`:** list H100 etc., generalise the five W100 sites in section 5, pass `--map` + a map-specific orders file; keep W100 default.
5. **Map upload:** the 5-step flow above, with check output shown and topology as a queued job.
6. **2D replay of finished runs from artifacts** (decisions/outcomes tables), independent of the observed guard.
7. **Observed live mode:** review `observed_runner` against the new runner, then update the hash (owner decision per the merge note).
8. **Polish:** font sizes, contrast, `:focus-visible`, dark theme via CSS variables, mobile map overlay overlap.
